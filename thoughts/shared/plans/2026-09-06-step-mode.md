# Step Mode Implementation Plan

## Overview

Let a developer *walk* a test run in a window: pause before each test, and at captioned points
inside a test, with a caption saying what is about to happen and controls to continue, skip the
current test, or let the rest of the run go.

The motivating use is diagnosis rather than CI. A suite of world-building fixtures is a
reproduction of a reported bug; being able to watch one happen at human speed is what makes it
useful for diagnosis and not only for a pass/fail number.

## Current State Analysis

**Runner** (`mod/factorio-test/runner.ts`): a state machine with a single `nextTask` and a
`ticksToWait` counter, driven from `on_tick`. Tests are made of *parts* (`Test.parts`); the runner
already runs them one after another, and `after_reload_script`/`after_reload_mods` already add
parts through `TestBuilder`. Async tests suspend between ticks via `waitForTestPart`.

**GUI** (`mod/factorio-test/test-gui.ts`): built by the framework bundle inside the mod under test,
only in graphics mode. Its buttons carry `tags.modName = "factorio-test"`, are dispatched by the
factorio-test mod (`mod/control/guiAction.ts`, `mod/control/test-gui.ts`), and call back into the
framework through the `factorio-test` remote interface. `Cancel` already maps to `cancelTestRun`.

**Config**: flows CLI → mod as a JSON settings blob (`cli/config/test-config.ts` →
`factorio-test-config` runtime-global setting → `mod/factorio-test/config.ts`).

### The constraint that shapes the design

An inline `step("caption")` in the middle of a test body — the obvious API — would need the test
function to suspend and resume, i.e. a coroutine. **Factorio's Lua does not have coroutines**:

> Some modules that are part of standard Lua are not accessible in Factorio's Lua environment,
> mostly to ensure determinism. These inaccessible modules are: `loadfile()`, `dofile()`,
> `coroutine`, `io` and `os`.
> — `doc-html/auxiliary/libraries.html`

This was confirmed empirically as well (`coroutine` is nil in the mod environment), so a step
boundary has to be a boundary the runner already has: the gap *between test parts*.

## Desired End State

```lua
test("connects an underground pipe", function()
    place_underground()
end)
  :step("place the covering tile", function()
    place_tile()
  end)
  :step("check the connector", function()
    assert_connected()
  end)
```

- Step mode off (the default): the parts run back to back, exactly as one test body would.
  Nothing about the test's behaviour or reporting changes.
- Step mode on: the run pauses before each test (caption = the test's path) and before each
  captioned part (caption = the step's caption). The GUI shows the caption and three buttons —
  **Continue**, **Skip test**, **Run the rest** — alongside the existing **Cancel**.

`factorio-test run -p ./my-mod -g --step "ice gap"` walks that fixture a step at a time.

## What We're NOT Doing

- An inline `step()` callable mid-function — impossible without coroutines (see above).
- Pausing between the two parts that `after_reload_*` adds: only parts with a caption pause.
- Any headless behaviour. Step mode needs a GUI to continue from; the CLI refuses `--step`
  without `--graphics`, and the mod ignores `step` (with a log line) when headless, so a
  mod that declares it in its own config still runs normally in CI.
- Keyboard shortcuts for the step controls. Worth adding later; it needs a prototype change.

## Architecture

### Pausing

`TestState` gains `stepMode` (effective, cleared by "run the rest"), `stepPause` (set while
waiting) and `stepAction` (the user's choice, consumed on the next tick). `TestRun` gains
`stepSkipped`.

`TestRunnerImpl.pauseForStep(caption, next)` sets `stepPause`, stashes `next` on the runner and
returns a `resumeStep` task. `tick()` refuses to advance while `stepPause` is set, so the runner
sits on that task. `requestStepAction()` (called from the GUI, through the remote interface)
clears `stepPause` and records the action; the next tick runs `resumeStep`, which dispatches:

| action     | effect                                                                     |
| ---------- | -------------------------------------------------------------------------- |
| `next`     | run the stashed task                                                       |
| `runRest`  | `stepMode = false`, then run the stashed task                              |
| `skipTest` | abandon the current test (see below)                                       |

Cancel keeps working while paused: `tick()` checks `cancelRequested` first, and `cancelTestRun()`
clears the pause.

### Skipping

- Paused *before* a test (nothing has run yet): raise `testSkipped` and move to the next sibling.
- Paused *between parts*: mark the run `stepSkipped` and go straight to `leaveTest`, so
  `after_test` and `after_each` still run. `leaveTest` reports `testSkipped` instead of
  `testPassed`, unless the test already has errors, in which case it is still a failure.

Both reuse the existing `testSkipped` event, so results, GUI and CLI output need no new outcome.

### Events and GUI

Three new events. `stepPaused { caption }` and `stepResumed` drive the step bar. `stepStarted
{ caption }` is raised when a captioned part actually begins, and is what `output.ts` logs as a
`STEP` line — logging it at pause time instead made the log and the "Next:" bar say the same
thing at the same moment, which reads as an off-by-one. The buttons go through `Misc.StepNext` /
`StepSkipTest` / `StepRunRest` and a new remote method `stepAction`.

### Holding the world still

While a step waits, the GUI sets `game.tick_paused`, so what is on screen is the state at the
step boundary rather than whatever it drifted into while you read the caption. `requestStepAction`
and `cancelTestRun` clear it again — the runner is driven by `on_tick`, which does not fire while
the game is paused, so anything that resumes a run has to unpause first. `load.ts` stops forcing
`tick_paused = false` for the duration of a pause. GUI clicks do still register while paused.

This also removes a trap: the test-part clock. `newTestRun` stamps `tickStarted` when the task is
*queued*, and a pause can sit between queueing and running for as long as the user takes, so
`async(n)` timeouts and `after_ticks` were being measured against think time and fired
immediately. `runTestPart` now re-stamps `tickStarted` when the part actually starts.

### Config

`step` in `FactorioTest.Config` and `TestRunnerConfig`; `--step` on the CLI (the first test
config field whose Commander key isn't the camelCase of its name, hence `optionKey` on the field
definition). `game.speed` is forced to 1 while step mode is on — the default of 1000 makes
watching pointless.

### Incidental fix

`after_test` hooks registered in one part were dropped at the part boundary, because each part
got a fresh `TestRun` with an empty `afterTestFuncs`. Rare with `after_reload_*` (the Lua state is
replaced anyway); common as soon as `.step()` exists. `newTestRun` now carries them forward.

## Testing

- `mod/factorio-test/test/meta.test.ts`: a `step mode` block driving the runner tick by tick and
  answering each pause — captions, no pause when off, no pause for skipped tests or after a
  failure, each of the three actions, cancel while paused, the events, and that `stepStarted`
  fires when a part runs rather than when it is queued.
- `cli/schema.test.ts`: `--step` ↔ `step` mapping, parameterized.
- `integration-tests/tests/config-options.ts`: `--step` and config-file `step` both error
  without `--graphics`; a mod-declared `step` is ignored headless and the run still finishes.
  The usage fixture gained a `.step()` part, so every headless run proves step parts still run
  back to back.
